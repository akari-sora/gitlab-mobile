# MR6c decisions

Decisions and hand-offs that implementation packets made binding. The breakdown (`mr6c-breakdown.md`) stays the plan; entries here win where they are more specific.

## C-D1. The v1 `io.gitlabmobile/agent_runs` channel (C1, !161)
Generated by `tool/bootstrap.py` (C1). C2a/C2b build on this table; changing it needs a new decision and a generator change in the same MR.

| v1 surface | Arguments, types, limits | Reply / enforcement |

Every method below requires `opSeq`. | Expected results use MethodChannel success maps containing `version: 1` and string `status`. | Common sequence | `opSeq`: integer, 1…9007199254740991; doubles and booleans rejected. Caller allocates a newer sequence; never replay an old operation. Cancellation recorded first prevents a delayed lower-sequence start from reviving work. |

Round-1 review fixes that refine the table (C1 `1cadf5b`): every start promotes to the foreground with the safe notification before it decides to stop; outside paths never stop a STARTING service; each service instance binds once to the permit lifetime it was started for; a release with a sticky cleanup failure still invalidates the current permit; pending start replies are answered outside promotion.

## C-D2. Hand-offs to C2b (from the C1 reviews)
- The `opSeq` high-water mark survives an engine or Activity restart in the same process. C2b seeds its counter from `opSeqFloor` in a `stale_operation` reply before the first real call; this is not an automatic retry of the user's operation.
- A permit whose creating start and adopting start both timed out cannot be released by a request-scoped release (`didRelease: false`). C2b defines how such an orphan ends (stopAll on the next foreground, or Activity destroy) and tests it.
- Native only bounds `title`/`text` (length, control characters). C2b must pass translated, generic work-status strings (D10/D12) and lock that with tests.
- Indonesian Android resources are emitted as both `values-in` and `values-id` (Android ≤14 maps `id` to `in`).

## C-D3. C2a acceptance: legacy fixtures and the model boundary (lead, 2026-10-27)
C2a's first run kept the plan's fail-closed default (no injected gate and no visibility predicate → no execution) and turned 260 legacy `test/ai` cases red, because standalone runners, coordinators and `tool/ai_live_smoke.dart` never supplied visibility.
- The default stays fail-closed. Legacy fixtures and helpers pass an explicit visible-foreground predicate (or the C2a fake gate); assertions are not weakened. `tool/ai_live_smoke.dart` passes an explicit always-visible predicate with a comment, since it runs on the desktop VM without an app lifecycle.
- `AiChatController` wires its real `appInForeground` predicate into the default gate for the runner and the coordinator (C2b later replaces the default with the native bridge). Without this the app would stop every AI send.
- The model ticket boundary checks execution eligibility, the run binding and the existing runner guards only. The GitLab client / 429 predicate (`clientMayStart`) stays a write-boundary guard ("client gate 仍獨立", breakdown C2b row; parent plan §15 row 29): a missing client predicate fails the write before port construction and the run continues with that tool result.

## C-D4. C2a review round 1 (lead, 2026-10-27)
- **Local foreground tickets have no total TTL.** A foreground run without a permit gets a local ticket that only rechecks real visibility at consume (D4). The 1000 ms total TTL applies to native permit tickets (D3) only. Reason: markDispatching includes the journal lock, a secure-storage read and an isolate write. A slow device or three conversations sharing the journal lock would otherwise refuse foreground writes with `ticketExpired` and void flushed approvals (Opus r1 m1).
- **The model boundary also stops on run drift.** It stops when writePolicyRevision, scopeRevision, consentHash or proposalEpoch changes (`executionRunCurrent`). This is intended and tested, and refines C-D3's "only eligibility, binding and runner guards" (m4).
- **REST rollback is not retried.** A failed dispatching→notExecuted rollback after flush is no longer retried. It stays `writeUncertain` and isolated with mutationCount 0, per D6; main previously retried once (m5).
- **Coordinator segment state is not restored.** Restoring an unsent segment keeps the coordinator's `_segmentGeneration`/`_segmentCreated` as advanced by `beginSegment()`. This is stricter and accepted (m6).
- **Snapshot defaults changed.** `AiWritePolicySnapshot.appInForeground` now defaults to false, and `clientMayStart` is a lazy getter, so a stored snapshot reads the live value. No code reads the client field from a stored snapshot; keep it that way (m7).

## C-D5. A normal service release rebinds approval-waiting runs to the foreground (lead, 2026-10-27)
C2b found that D7 (release the service when every run only awaits approval) conflicts with C2a's immutable permit-bound run binding: after a normal release, a later foreground approval is refused (`notExecuted`, `backgrounded`), and D4 forbids a foreground shortcut for a permit-bound run.
- On a **normal release** (`releaseRuns` → `released`, not an invalidation: user stop, timeout, service/activity destroyed, or a lost callback), each run bound to that permit that is waiting only for approval gets an explicit binding transition to a permitless foreground binding. The transition is a single core API, called only by the bridge for the exact released permit.
- After the transition, approval and execution use the local foreground gate: real visibility at acquire and consume, no TTL (C-D4). Approval already requires real visibility. Tickets issued under the old binding stay invalid, and a stale reply is still discarded.
- If the app goes to the background again, the run needs a new permit (a new `startRuns`). Nothing executes in the background under the old permit.
- An **invalidation** (`permitInvalidated`) never rebinds. It ends or pauses the run as before.

## C-D6. Notification event kinds and the run-limit refusal (lead, 2026-10-27, C2b review round 1)
Codex I1 found a finishing-mode model failure (`AiRunEnd.toolBudget` with a non-null failure) published as `completed`; GLM noted that every budget or limit end maps to `completed` and that the fourth-run refusal publishes `failed`. C3 consumes only these typed events, so the kind must not overstate the outcome. Conservative mapping, decided by the lead:
- `failed`: the run recorded a final failure, whatever its `AiRunEnd` (including `toolBudget` with a failure), or ended `failed`.
- `completed`: only `done` with no recorded failure.
- `interrupted`: `stopped`, `stoppedBySettings`, `newSecret`, and every end that cut the answer short without a failure: `maxTokens`, `contentFilter`, `refusal`, `toolBudget`, `toolBudgetNoAnswer`, `contextTooLong`, `tokenBudget`.
- `needsApproval` is unchanged.
- The fourth-run refusal (three running) is **not sent**. It publishes no notification event and is not a generic failure. The controller records it as an execution pause with a dedicated reason (`AiExecutionPauseReason.runLimit`) and no new strings. C5 owns the pause UI and its text.

## C-D7. C3 notification UI choices (lead, 2026-10-28)
- **Where permission is asked:** in the chat's send action, before `session.send`. That is the only path that reaches `beginRun` and the foreground service, so it is always a user action, never app start-up. An explanation comes first, then the system request. On denial, on "not now" or when no request is available, the send continues and a one-time disclosure names the absent reminders and the 30-minute expiry. iOS never asks.
- **Remembered in memory only, once per process.** CLAUDE.md's Persistence list is closed and the plan grants no new storage key.
- **Follow-up in C3 FIX1:**
  - The core gains an `areNotificationsEnabled()` query.
  - The UI skips the explanation when notifications are already on.
  - When they are off, the UI shows the disclosure instead of asking again.
- **Taps:**
  - A warm-start tap that arrives before the app reports it is in the foreground waits for the lock decision (`away`), so a tap never navigates under the lock.
  - `take()` runs before the shell is brought forward and is rechecked afterwards; a relock in between drops the tap.
  - A tap is consumed even when an open editor refuses to close, which matches shared links.
- **NOT_RUN:** scrolling to the card in a long list, and every device behaviour (drawer, lock screen, permission dialog, cold and warm taps), which are left to C8.

## C-D8. One device-scoped "notification permission asked" marker (lead, 2026-10-28, C3 review round 2)
On Android 13+ a fresh install has notifications off until the user answers, and the pinned plugin's `areNotificationsEnabled()` cannot tell "never asked" from "denied". C3 FIX1 therefore skipped the first request (R2-I1). Decision:
- **The marker:** `flutter_secure_storage` key `gitlab_mobile_ai_run_notice_asked_v1`, value `1`. It is device-scoped like the appearance key, holds no content, and is written after the first system request returns, whatever the answer. It is not removed with an account.
- **Behaviour at the user's send:**
  - notifications enabled: no explanation and no request;
  - disabled and not yet asked: explanation, then the system request;
  - disabled and already asked: the existing one-time disclosure and no re-ask.
- **An unreadable or unavailable marker** counts as "not asked". That costs at most one extra explanation; it never suppresses the first request. A failed write is retried at the next ask.
- **Channels:** "reminders are off" may be claimed only when app notifications or the **approval** channel are off. A disabled results channel alone does not trigger the disclosure (R2-M1).
- **Docs:** `CLAUDE.md` Persistence lists the key.

## C-D9. C4 extends the v1 channel surface for stop all (2026-10-28)
C-D1 requires a decision for any change to the v1 channel surface. C4 (MR !182) adds:
- **`stopAllLabel`** — an optional, bounded string on `startRuns` and `updateProgress`, Dart-supplied from `l10n.aiRunServiceStopAll` like `title` / `text`. Native shows the stop-all action only with a valid label; no Kotlin text.
- **`startRequestId` on `permitInvalidated`** — the callback may carry 3 or 4 fields; the fourth names the start request that was pending when native invalidated. Older 3-field callbacks stay valid.
- **Ordering.** Native `notifyInvalidated()` completes the pending start (`finishPending`, a `rejected/user_stop` reply) before it sends the callback, and the callback may be lost. Dart therefore treats a `user_stop` rejection of the **current** start request as the global stop itself, and correlates the later callback by `startRequestId` or by the current permit. Each stop is consumed once; a callback for an already-stopped, released or older permit never emits another stop (review round 1, F1/F2).
- Generator and Dart change in the same MR, as C-D1 requires.

## C-D10. C6 task-back results and a side-effect-free sequence probe (2026-10-28)
- **Native method:** `moveTaskToBack` keeps the existing v1 envelope and `opSeq`-only arguments. It validates syntax and consumes the sequence before checking the current resumed Activity. It calls `Activity.moveTaskToBack(true)` once and maps the boolean to `moved` / `not_moved`; `true` also covers an already-background task. Flutter's root page does not imply Android task-root, so `nonRoot=true` supports both launcher and link entry. A finishing/destroyed or non-resumed Activity rejects with `foreground_required`; exceptions use only `security_exception` / `move_failed`, without exception text. This method neither changes permits nor starts/stops a service. Android supports the API from API 1; other Dart platforms return typed `unsupported` without calling a channel.
- **Probe:** C2b used the old unsupported back stub to seed `opSeq`. C6 replaces that with `updateProgress(opSeq, permitId: "sequence-probe", workCount: 1, step: 0)`. Native permit IDs are generated UUIDs and can never match that non-UUID ID. The request consumes the sequence and returns `rejected/permit_inactive`, or reports `stale_operation` with the floor, without changing progress or moving the task. There is no new native method or automatic replay of a back operation.
- **Dart/UI handoff:** `AiBackgroundExecution.moveTaskToBack({required bool Function() isBackEligible})` returns `Future<AiTaskBackResult>`: `moved`, `notMoved`, `notEligible`, `unsupported`, `foregroundRequired`, `unavailable`, or `failed`. It uses the existing shared operation queue, rechecks the owner, real visibility and required live eligibility predicate after waiting/seeding, validates replies, and never starts a run. The UI predicate checks the current/mounted shell, app-lock, root route (including dialog/keyboard), no detail, home tab and `backProtectedCount > 0`; detail/tab back still consumes and returns first. There is no await between the final predicate check and the channel invocation. Approval-waiting and paused work need no active native permit. A timeout, malformed reply, missing channel or changed owner returns `unavailable`, without retry or Activity finish fallback. A timed-out invocation cannot be cancelled: its native movement outcome remains unknown and the original call may already have moved the task or may be processed later. Synthetic late-reply tests prove no Dart retry, not absence of native movement.
- **Debug evidence:** the existing explicitly registered debug QA adapter exposes `taskBackCalls({})` → `{version: 1, count: <integer>}`. The counter increments immediately before the actual Activity API call, including an API call that throws or returns false, and `reset({})` clears it. Failed validation/lifecycle checks and sequence probes do not increment it. The counter is memory-only, contains no content, and adds no production QA method/channel.
- Official semantics: [Android Activity.moveTaskToBack](https://developer.android.com/reference/android/app/Activity#moveTaskToBack(boolean)); [Flutter MethodCallHandler](https://api.flutter.dev/javadoc/io/flutter/plugin/common/MethodChannel.MethodCallHandler.html). Actual Activity/predictive-back behavior stays in C8.
