Decisions and hand-offs that implementation packets made binding. The breakdown (`mr6c-breakdown.md`) stays the plan; entries here win where they are more specific.

## C-D1. The v1 `io.gitlabmobile/agent_runs` channel (C1, !161)
Generated by `tool/bootstrap.py` (C1). C2a/C2b build on this table; changing it needs a new decision and a generator change in the same MR.

Round-1 review fixes that refine the table (C1 `1cadf5b`): every start promotes to the foreground with the safe notification before it decides to stop; outside paths never stop a STARTING service; each service instance binds once to the permit lifetime it was started for; a release with a sticky cleanup failure still invalidates the current permit; pending start replies are answered outside promotion.

## C-D2. Hand-offs to C2b (from the C1 reviews)
- The `opSeq` high-water mark survives an engine or Activity restart in the same process. C2b seeds its counter from `opSeqFloor` in a `stale_operation` reply before the first real call; this is not an automatic retry of the user's operation.
- A permit whose creating start and adopting start both timed out cannot be released by a request-scoped release (`didRelease: false`). C2b defines how such an orphan ends (stopAll on the next foreground, or Activity destroy) and tests it.
- Native only bounds `title`/`text` (length, control characters). C2b must pass translated, generic work-status strings (D10/D12) and lock that with tests.
- Indonesian Android resources are emitted as both `values-in` and `values-id` (Android ≤14 maps `id` to `in`).

## C-D3. C2a acceptance: legacy fixtures and the model boundary (lead, 2026-10-27)
C2a's first run kept the plan's fail-closed default (no injected gate and no visibility predicate → no execution) and turned 260 legacy `test/ai` cases red, because standalone runners, coordinators and `tool/ai_live_smoke.dart` never supplied visibility.
- The default stays fail-closed. Legacy fixtures and helpers pass an explicit visible-foreground predicate (or the C2a fake gate); assertions are not weakened. `tool/ai_live_smoke.dart` passes an explicit always-visible predicate with a comment, since it runs on the desktop VM without an app lifecycle.
- `AiChatController` wires its real `appInForeground` predicate into the default gate for the runner and the coordinator (C2b later replaces the default with the native bridge). Without this the app would stop every AI send.
- The model ticket boundary checks execution eligibility, the run binding and the existing runner guards only. The GitLab client / 429 predicate (`clientMayStart`) stays a write-boundary guard ("client gate 仍獨立", breakdown C2b row; parent plan §15 row 29): a missing client predicate fails the write before port construction and the run continues with that tool result.

## C-D4. C2a review round 1 (lead, 2026-10-27)
- **Local foreground tickets have no total TTL.** A foreground run without a permit gets a local ticket that only rechecks real visibility at consume (D4). The 1000 ms total TTL applies to native permit tickets (D3) only. Reason: markDispatching includes the journal lock, a secure-storage read and an isolate write. A slow device or three conversations sharing the journal lock would otherwise refuse foreground writes with `ticketExpired` and void flushed approvals (Opus r1 m1).
- **The model boundary also stops on run drift.** It stops when writePolicyRevision, scopeRevision, consentHash or proposalEpoch changes (`executionRunCurrent`). This is intended and tested, and refines C-D3's "only eligibility, binding and runner guards" (m4).
- **REST rollback is not retried.** A failed dispatching→notExecuted rollback after flush is no longer retried. It stays `writeUncertain` and isolated with mutationCount 0, per D6; main previously retried once (m5).
- **Coordinator segment state is not restored.** Restoring an unsent segment keeps the coordinator's `_segmentGeneration`/`_segmentCreated` as advanced by `beginSegment()`. This is stricter and accepted (m6).
- **Snapshot defaults changed.** `AiWritePolicySnapshot.appInForeground` now defaults to false, and `clientMayStart` is a lazy getter, so a stored snapshot reads the live value. No code reads the client field from a stored snapshot; keep it that way (m7).

## C-D5. A normal service release rebinds approval-waiting runs to the foreground (lead, 2026-10-27)
C2b found that D7 (release the service when every run only awaits approval) conflicts with C2a's immutable permit-bound run binding: after a normal release, a later foreground approval is refused (`notExecuted`, `backgrounded`), and D4 forbids a foreground shortcut for a permit-bound run.
- On a **normal release** (`releaseRuns` → `released`, not an invalidation: user stop, timeout, service/activity destroyed, or a lost callback), each run bound to that permit that is waiting only for approval gets an explicit binding transition to a permitless foreground binding. The transition is a single core API, called only by the bridge for the exact released permit.
- After the transition, approval and execution use the local foreground gate: real visibility at acquire and consume, no TTL (C-D4). Approval already requires real visibility. Tickets issued under the old binding stay invalid, and a stale reply is still discarded.
- If the app goes to the background again, the run needs a new permit (a new `startRuns`). Nothing executes in the background under the old permit.
- An **invalidation** (`permitInvalidated`) never rebinds. It ends or pauses the run as before.

## C-D6. Notification event kinds and the run-limit refusal (lead, 2026-10-27, C2b review round 1)
Codex I1 found a finishing-mode model failure (`AiRunEnd.toolBudget` with a non-null failure) published as `completed`; GLM noted that every budget or limit end maps to `completed` and that the fourth-run refusal publishes `failed`. C3 consumes only these typed events, so the kind must not overstate the outcome. Conservative mapping, decided by the lead:
- `failed`: the run recorded a final failure, whatever its `AiRunEnd` (including `toolBudget` with a failure), or ended `failed`.
- `completed`: only `done` with no recorded failure.
- `interrupted`: `stopped`, `stoppedBySettings`, `newSecret`, and every end that cut the answer short without a failure: `maxTokens`, `contentFilter`, `refusal`, `toolBudget`, `toolBudgetNoAnswer`, `contextTooLong`, `tokenBudget`.
- `needsApproval` is unchanged.
- The fourth-run refusal (three running) is **not sent**. It publishes no notification event and is not a generic failure. The controller records it as an execution pause with a dedicated reason (`AiExecutionPauseReason.runLimit`) and no new strings. C5 owns the pause UI and its text.
