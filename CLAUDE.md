## Toolchain and commands

Flutter is pinned to **3.47.2** (Dart 3.13.2) through `.fvmrc`; always use the `fvm` prefix so the system `flutter` cannot drift. `pubspec.lock` is committed and enforced.

```sh
fvm flutter pub get --enforce-lockfile
fvm flutter analyze --no-pub
fvm flutter test --no-pub
fvm flutter test --no-pub test/session_test.dart                       # one file
fvm flutter test --no-pub test/session_test.dart --plain-name 'select'  # one test by name substring
fvm exec bash ci/check.sh   # CI-equivalent: analyze + tests with coverage + JUnit; needs GNU timeout (brew coreutils)
```

The `ci/*.sh` scripts call bare `flutter` / `dart`, and this machine has no system Flutter on `PATH`, so run them through `fvm exec`. Locally `ci/check.sh` exits 1 after a green analyze/test run because its final screenshot-thumbnail step runs `pip install Pillow` against Homebrew's externally-managed Python; the real verdict is in `ci-output/check-status.txt` (`analysis_exit` / `test_exit` / `report_exit`).

Python-side checks (also run in CI):

```sh
python3 -m unittest discover -s ci/tests -p '*_test.py' -v
python3 -m unittest discover -s tool/tests -p 'test_*.py' -v   # bootstrap, signing, icon and l10n checks
python3 tool/l10n.py              # regenerate lib/l10n/strings*.g.dart after editing lib/l10n/arb
python3 -m compileall -q ci tool
```

Native runners (`android/`, `ios/`, `.metadata`) are **not committed**. `tool/bootstrap.py` generates them with `flutter create` and then hardens them (no cleartext HTTP, no backup, keychain entitlements, OAuth URL scheme `io.gitlabmobile.app://oauth/callback`). It also adds the link trampoline (`LinkActivity`, below), makes `MainActivity` a `FlutterFragmentActivity` with AppCompat launch/normal themes (required by `local_auth` for the app lock) and records the iOS Face ID reason. It refuses to overwrite existing native directories and rejects any Flutter that is not 3.47.2, so pass the fvm binary:

```sh

python3 tool/bootstrap.py --flutter .fvm/flutter_sdk/bin/flutter --check-sdk
fvm exec bash ci/build_android.sh                                    # gitlab-flavor debug APK + build-metadata.json + SHA256SUMS
```

Smoke tools use the production `GitLabApi`:

```sh

```

`run_live_smoke.py` finds `dart` through `PATH`, so put `.fvm/flutter_sdk/bin` on `PATH` first. Never pass a token on the command line or as a Dart define.

Analyzer settings are strict (`strict-casts`, `strict-inference`, `strict-raw-types`, `unawaited_futures`, `avoid_print`) and CI treats analyzer **info** diagnostics as failures (an unused import has already broken a pipeline). More than half of the Dart files differ from `dart format` output; do not mass-format the repository, format only the lines you touch.

## Architecture

### Layering

- `lib/core/` is plain Dart (only `providers.dart` imports Flutter/Riverpod): instance parsing, HTTP client, failures, pagination, models, OAuth PKCE, unified-diff parsing.
- `lib/features/auth/` owns the session lifecycle. Disk writes are only the secure-storage keys and the artifact temp directory listed under Persistence.
- `lib/features/projects/` holds typed list controllers; `lib/features/workspace/` holds the screens; `lib/features/shell/` is the bottom-nav shell; `lib/shared/` is theme, Markdown and reusable widgets/helpers.
- `lib/core/workspace_api.dart` is `part of 'gitlab_api.dart'`: it adds generic `record` / `records` / `writeRecord` / `removeRecord` over untyped `Json` maps plus typed wrappers (issues, MRs, notes, files, branches, tags, pipelines, jobs, releases, todos). Most workspace screens consume these `Json` maps directly through the `valueText` / `valueInt` / `valueObject` helpers in `lib/shared/workspace_ui.dart`.

### Identity and the API client

`GitLabInstance.parse` accepts HTTPS only and keeps scheme, host, port and installation subpath; `Account.key` is `instance.key#userId`; projects are addressed by numeric ID after resolution. Every cache, draft and controller is bound to one `Account`.

`GitLabApi` invariants (keep them when adding endpoints):

- One immutable account per client. `instance.allowsApi(uri)` gates every request: same origin, `/api/v4` prefix, no `.`/`..` segments, no token-like query keys. Redirects are never followed (`redirectBlocked`). The !5 artifact download is the exception: authenticated first hop with `followRedirects: false`, exactly one https `Location`, fetched by an isolated bare Dio with no credential headers, 256 MiB budget, throttled progress.
- Responses are streamed against a byte budget (4 MiB default, `maxTextBytes` 2 MiB / `maxTextLines` 20000 for text); overruns become `tooLarge`, binary bytes become `unsupported`.
- A 429 `Retry-After` is remembered in `_retryAt` and later calls fail fast with `rateLimited` until it passes.
- Writes are never retried automatically. A transport error on a non-GET/HEAD request is `writeUncertain`, and an OAuth 401 refresh only replays GET/HEAD.
- `close()` cancels all in-flight requests; a closed client only ever throws `cancelled`.

`ApiFailure` / `FailureKind` is the single error surface for GitLab traffic; AI provider traffic uses `AiFailure`. Both implement `UserFacingFailure`, which `showFailure` accepts; `FailureNotice` stays GitLab-only. `safeFailure()` wraps anything unknown as `invalidResponse`. User-facing `title` / `detail` strings live on the failure itself and come from `l10n` like all UI text. HTTP 404 maps to `invisible`, which the UI must present as ambiguous (see `AGENTS.md`).

Pagination (`lib/core/pagination.dart`): `nextPageUri` parses `Link` / `X-Next-Page`, and `checkedPageUri` rejects any cursor that changes path, drops or alters the caller's non-pagination query, adds scope filters, or does not progress. GitLab expands omitted `false` defaults into the `Link` header, which is why `_falseDefaults` exists. `GitLabApi._validateContinuation` re-checks a caller-supplied `next` against the first-page URL on every call.

### Session, generation and cancellation

`SessionController` (`ChangeNotifier`, exposed only through `sessionProvider`) holds the saved accounts, the `active` account and its `api`. `connect` / `select` / `connectOAuth` take an `_operation` ticket and drop their result if the ticket is stale; `select` re-validates `/user` and rejects a mismatched user ID. Every `_activate` and `endSession` increments `generation`, and `main.dart` keys `AuthenticatedApp` on `ValueKey(session.generation)`, so the entire authenticated widget tree is rebuilt on account switch and the previous `GitLabApi` is closed. `endSession` is local only and does not revoke tokens.

Offline read-only mode (C3c; `AGENTS.md` has the contract). Resume and `select` check identity with `identityCheck()` (`lib/core/offline_repository_api.dart`), whose sealed `IdentityVerdict` is `ok`, `refused401` / `refused403` (GitLab JSON only), `noVerdict` (network, 5xx, 429, redirect, 2xx that is not GitLab JSON) or `unknown`. When auto-resume gets `noVerdict` and `OfflineGate.check` (`lib/features/offline/offline_gate.dart`) qualifies the account (no `offline_refused` marker, readable C3 key and index with a complete snapshot, validated within 30 days by the device clock, the app-lock setting read without failure), `_enterOffline` sets `session.offline` (an `OfflineSession`) and leaves `active` and `api` null: there is no `GitLabApi` in this mode. It takes no new ticket but hands the resume ticket to `offline.validationTicket`, ends `initializing`/`resuming`, keeps the account's disk (`diskRetainedAccountKey`), increments `generation` and moves the C3 coordinator `closed → offlineReadOnly`. The resume screen offers 離線瀏覽 (`canEnterOffline` / `enterOffline()`) while `/user` still runs. `main.dart` binds the `appLockProvider` controller with `bindOfflineAppLock` and starts it before `initialize`, then checks `session.offline` before `resuming` and `initializing` and renders `OfflineApp` (`lib/features/offline/offline_app.dart`): its own `MaterialApp` keyed by `ValueKey(session.generation)`, under `OfflineLockGate` (the same controller's `AppLockGate`, plus a cover while the setting is unread or unreadable, `offlineCovering`, with a retry through `reload()`), wrapped in `NetworkBoundary(offlineSnapshot)` and an `OfflineScope` whose `OfflineRepositories` has no client. It shows the saved projects (C3b's browser and 管理離線專案), the banner by `offline.reason` and an account row; no bottom navigation, search or AI. The only network request is the isolated, single-flight `/user` probe (`probeOffline`: manual, on resume, backoff 15 s → 5 min while in the foreground). The mode allows no local AI writes: entry closes `session.localWritesClosed` first, so `main`'s AI startup recovery (`_SessionRecovery.runAi`, history and journal) starts no step, and `settleLocalWrites` gives the step already running the recovery timeout (`barrierLimit`) to finish; if it does not, entry is refused. Recovery resumes once the mode ends (sign-in screen or online), as before. A background `ok` only sets `connectionRestored`; 重試連線 and 切換到線上 call `probeOffline(switchOnline: true, projectId:)`, which activates the account after a fresh `ok` and sets the existing `'repository'` resume target for the project being read. That project is tracked from the routes `openSnapshot` pushes (`SnapshotRouteArguments`, observed by `SnapshotReadingObserver`), so it holds whether the snapshot was opened from the home list or 管理離線專案, and clears on the way back. A GitLab 401 or another user ID fences and clears the account and leaves (the sign-in screen says the data is being deleted, then whether it was, from the bounded clear result, so a clear that times out says it is retried at the next start); a 403 writes the refusal marker and leaves with the data kept; `unknown` leaves with the data kept; passing 30 days leaves with a message. `select`, `connect`, `connectOAuth` and `remove` return at once while offline; the ways out are 改用其他帳號 (the D1 confirmation, then `endSession`, whose leaving account is `active ?? offline ?? resumingAccount ?? diskRetainedAccountKey`), going online and the verdicts. Launcher shortcuts are bound to no account while offline, and leaving for the sign-in screen clears the published ones; incoming links stay queued (the shell shows that one waits). `offlineModeShellReady` in `offline_gate.dart` is on; tests can turn it off with `offlineModeShellReadyForTesting`.

OAuth PKCE is fully wired, but `oauthApplicationIdFor` in `lib/core/oauth.dart` is an intentionally empty map: the OAuth path stays inert until a real application ID is registered per instance. Do not invent one.

### Controller pattern

List/detail state uses `ChangeNotifier` plus an integer epoch (`_epoch` / `_generation`): bump it at the start of each refresh, check `_current(epoch)` after **every** `await`, and guard `notifyListeners` with `_disposed`. A failing later page goes to `pageError` / `failedMore` and keeps the rows already loaded. `RecordController` is the generic `Json` list controller used by workspace screens; `ProjectController` and `RepositoryController` are the typed ones (the latter also caches directory snapshots in memory, bound to one commit SHA). Follow the same shape for new screens.

Riverpod holds the session and device-wide controllers (`lib/core/providers.dart`; AI settings are in `lib/features/ai/ai_settings_provider.dart`); per-screen state stays in widgets and controllers. Screens receive `api` and `account` explicitly through constructors; do not introduce widget-tree providers for per-screen state without a reason.

### Persistence

These are the only disk writes. Repository-derived disk content is limited to secure editor drafts, recent-project IDs and display names, transient artifact/attachment caches, the temporary media playback directory, the encrypted read cache, explicitly saved offline repository snapshots, and opt-in encrypted AI chat history below. Search history and running-job logs are not persisted; verified terminal-job log tails are allowed only through the read-cache contract below. `clearSecureDrafts(account)` runs before an account is removed. The `db12b41` phone build predates the appearance, last-account, sign-out, recent-project and artifact-cache entries.

Demo mode writes nothing: its account, sample data, drafts, recent projects, appearance, AI settings, AI history and AI write journal all live in memory and are dropped when the demo ends (see Demo mode below). The one exception is the plugins' own transient copy when a file or image is picked for an attachment (image_picker / file_picker, deleted by `discardPickedCopy` right after the bytes are read), as outside the demo.

Through `flutter_secure_storage`:

- Account list (`SecureAccountStore`, key `gitlab_mobile_accounts_v2`; v1 is read for migration, then deleted).
- Editor drafts keyed `draft.v2.<base64url(account.key)>.<base64url(resource)>`.
- Appearance, key `gitlab_mobile_appearance_v1`, value `<ThemeMode.name>|<0|1>` (theme mode and the dynamic-colour flag). A bare mode name from !3 still decodes and keeps the default (dynamic colour off). Device-scoped, shared by every account.
- App lock, key `gitlab_mobile_app_lock_v1`, value `1` while on (deleted when turned off). Device-scoped like the appearance. Turning it on requires a passing device check (`local_auth`, biometrics or the screen lock); while locked, `AppLockGate` covers the app and system back cannot pop the pages behind it (on the first page Android still sends the app to the background, and it stays locked).
- Last active account, key `gitlab_mobile_last_account_v1`. Auto-resume re-validates `/user`. This key is cleared only on a GitLab JSON 401 or a different user ID; a 401 or 403 that is not GitLab JSON, and any other failure without an identity verdict, keep it so the next start does not delete the account's data. Sign-out marker `gitlab_mobile_sign_out_pending_v1`: auto-resume never runs while the marker is set.
- Recent project, one record per account, key `recent_project.v1.<base64url(account.key)>`: numeric project id and the name shown on the launcher shortcut. Cleared with the account.
- Update check at start-up, key `gitlab_mobile_update_check_v1`, value `1` or `0` (gitlab and play builds only). Device-scoped.
- AI run notification permission asked, key `gitlab_mobile_ai_run_notice_asked_v1`, value `1`. Device-scoped, written after the first notification permission request returns, whatever the answer; not removed with an account.
- Language, key `gitlab_mobile_language_v1`, value `<tag>|<device language tags when picked, comma-separated>` such as `ja|en-US,fr-FR`; no key means the app follows the device's languages (English when none is translated). The most recent change wins: when the device's languages (or the system's per-app language) change after a pick, the pick is dropped and the key deleted. Device-scoped. `main` applies it before the first frame.
- Read-cache preference, key `gitlab_mobile_read_cache_v1`, device-scoped string `1` or `0`; confirmed absence means on. An invalid value or unavailable storage closes disk use without deleting existing data during ordinary reads/startup. Writes require exact readback; a failed write does not prove that off was persisted.
- Read-cache encryption key, `read_cache_key.v1.<base64url(account.key)>`, a base64url-encoded random 32-byte key per account. Names use `base64Url.encode(utf8.encode(account.key))`, including standard padding. `ReadCacheDiskCoordinator.instance` serializes creation and I/O, writes and reads back the key, and clears old files under a durable intent before replacing an absent/malformed key when files remain. An unavailable key permits no ordinary read, write or file cleanup; retries are at 1, 5 and 30 seconds and on resume. Explicit clear still attempts directory deletion if key deletion fails.
- Read-cache pending clear, `read_cache_clear_pending.v1.<base64url(account.key)>`, non-secret JSON `{version:1,intentId,reason,requestedAt}`. The opaque 32-hex intent ID and UTC timestamp contain no content; reasons are `scopeInvalidation` (crash-safe scoped eviction), `accountClear` (D1 or explicit clear), `keyRepair` (old-file removal before replacement) and `startup` (recovery cleanup). Unknown/malformed markers also require full-account startup cleanup. The coordinator owns marker revisions, reuses a confirmed intent within one batch and prevents an older scope completion from removing a newer full-clear intent. `ReadCacheSecureInventory` is an in-memory `readAll` result restricted to these key/marker prefixes, with separate read status and malformed names/values; it has no separate persisted inventory key and never owns AI entries. Unreadable inventory is not empty. Undecodable names trigger trusted read-cache-root cleanup and deletion of only the exact malformed secure-storage names, never a path derived from those names.
- Offline repository key (C3), `offline_repo_key.v1.<base64url(account.key)>`: a random 32-byte root key per account with the same ThisDeviceOnly options as the read-cache and AI keys, separate from the read-cache key so each namespace can be crypto-shredded on its own. Reads are three-state (found/absent/unavailable), creation is single-flight with readback, and a malformed key counts as absent. HKDF-SHA256 (salt `mergeline-offline-repo`, 32 bytes) derives the AES-256-GCM data key (info `offline-repo-data-v1`) and the HMAC naming key (info `offline-repo-names-v1`); the save worker isolate receives only those subkeys. An account-level clear (every session exit, terminal 401, different user ID, account removal, settings "clear cache", turning the offline cache off) shreds this key and the read-cache key; 全部刪除離線專案 shreds only this one; deleting one snapshot shreds neither (its leftover ciphertext stays decryptable while the key exists).
- Offline identity refusal (C3c), `offline_refused.v1.<base64url(account.key)>`, value the UTC time of a GitLab JSON 403 from `/user`. It blocks offline read-only mode for that account across restarts until a later `/user` returns the same numeric user ID, which deletes it (a same-account retry that fails again does not). If writing it fails, the account-level clear runs instead; an unreadable marker counts as present. The account-level clear deletes it; a C3-only clear keeps it.
- Offline repository pending clear, `offline_repo_clear_pending.v1.<base64url(account.key)>`: written before a C3-only namespace clear (全部刪除離線專案) stops the workers, deletes the key and then `offline_repo/<hash>/`; removed last. Startup cleanup handles it like the read-cache marker.
- AI provider settings, key `gitlab_mobile_ai_providers_v1`: device-scoped versioned JSON with provider configuration and revision, never API keys. One live `AiSettingsController` owns each store per process (all `SecureAiStore` wrappers share the device owner); repeated construction returns that same instance until disposal. Replacement construction is refused while a disposed owner still has pending mutations, and ownership releases after those mutations drain. `aiSettingsProvider` is app-level, does not use autoDispose, and lives above the account-keyed tree so account/generation changes do not dispose the device owner. A secure factory returns the existing device owner regardless of the storage instance passed; disposing any reference disposes that shared owner. Settings controllers do not synchronize peers. The reserved preset `gitlab-mobile:deleting-provider` is a durable deletion marker, hidden from active providers; deletion revokes account consents first, then removes the key, then the provider. Startup/next access resumes the marker before same-ID recreation. If a cleaning fence blocks consent revocation without a durable account tombstone, deletion/reset throws typed `cleaning`, retaining the provider marker and key for retry; a tombstoned account may be skipped because cleanup deletes its record. Endpoints are validated before storage. Provider order is persisted; the first provider is the device default, and editing preserves its position. Caps include the output-token limit (4096 for older records without that field); changing caps bumps the recipient revision.
- Structurally decoded AI providers with invalid endpoints are classified as malformed before publication, so settings never builds consent rows for them. Malformed AI provider settings have an explicit confirmed **Reset AI providers** action in settings. Reset removes the device-wide provider list, all stored provider keys and every account's provider consents; account history and preferences remain separate.
- AI provider keys, one key per provider at `ai_key.v1.<base64url(providerId)>`. Values shorter than four characters are rejected. Keyless presets do not create an entry. A separate non-secret `ai_key_binding.v1.<base64url(providerId)>` digest binds the credential to the normalized origin/base path and authentication style. Coordinated provider/key saves publish only after both writes succeed; startup deletes a credential and its binding when they mismatch after an interrupted replacement. Failed legacy key replacements preserve the previous binding and recipient revision; keyed-to-keyless saves delete before publishing and restore the old credential/binding on failure. Pre-binding credentials migrate before replacement.
- AI account settings, one versioned record per account at `ai_account.v1.<base64url(account.key)>`: per-provider consent hash, readable summary and grant time (recipient/policy derived from the normalized preset endpoint; request-owned versions/categories retained, with mismatched hashes refused); history enabled and retention days; and the conversation token cap. Since MR6b-1 the payload is version 2. It adds the write ceiling and the starting level (both default `lowRiskAuto`; the start is never above the ceiling and never `conversationGrant`), a write-policy revision bumped by ceiling changes, the AI-attribution switch (default off), and each consent's agreed ceiling. Version 1 records migrate in memory, with every old consent read-only, and are saved as version 2 on the next write.
- AI history encryption key, one 32-byte key per account at `ai_history_key.v1.<base64url(account.key)>`. Enabling history writes this key before setting `history.enabled`; a missing key for enabled history is `keyMissing` and must never cause automatic file deletion or replacement-key creation.
- History-only clear has a separate durable pending marker, `ai_history_clear_pending.v1.<base64url(account.key)>`, written before disabling or deleting history and deleted only after files and the encryption key are removed. A pending marker survives restart, blocks enabling and writing history even after disable/enable, is included in secure inventory/orphan cleanup, and offers retry; it never revokes consents or removes account preferences. A failed initial marker write leaves data intact and does not claim a durable pending marker.
- AI cleanup tombstone, `ai_history_tombstone.v1.<base64url(account.key)>`, retained until every AI cleanup step succeeds so start-up recovery can continue an interrupted removal.
- AI write-journal key, one 32-byte key per account at `ai_write_journal_key.v1.<base64url(account.key)>` (`SecureAiJournalKeyStore`, the same device-only options as the other AI keys). It is created before the account's first journal file, key first and read back. It is deleted only by account removal (after the journal's isolation check, inside the tombstone pipeline), by a journal reset, or by orphan cleanup once the account list has loaded. A missing or unreadable key blocks AI writes and never causes deletion or a replacement key. History settings and provider resets never touch it.
- AI write-journal reset marker, `ai_write_journal_reset_pending.v1.<base64url(account.key)>`, the confirmation time in ISO-8601 UTC. A reset writes it before deleting anything and deletes it last. An interrupted reset resumes at the next start, or before the account's next write; removal and orphan cleanup also delete it. Both journal entries are in the secure inventory.

Encrypted read cache: `getApplicationSupportDirectory()/read_cache/<sha256(account.key) first 32 hex>/`, with `index.v1.bin`, entries `e_<32 lowercase hex>.v1.bin` and exclusive temporary files `<entry-or-index filename>.<32 lowercase hex>.tmp`. Entry names are the first 32 hex digits of HMAC-SHA256 over the canonical key, using an HKDF-SHA256 key derived with info `read-cache-names`. Both entries and index use AES-256-GCM, a fresh 12-byte nonce, a 16-byte tag and AAD binding `read_cache`, version, account and file name (29-byte envelope overhead). Each entire plaintext entry, including its four-byte metadata length and metadata, is at most 1 MiB for JSON/files or 2 MiB for a terminal log; the index is at most 256 KiB plaintext and 2,048 entries. Encrypted files, indexes and temporary files count toward 32 MiB per account and 96 MiB per device; capacity eviction is LRU among eligible entries. Entries expire at age >=7 days; future `fetchedAt` is invalid. Activation removes expired/unreadable entries and temporary files older than one hour. The per-account write queue holds at most 2 MiB of serialized plaintext, dropping the oldest queued entries on overflow; index commits batch at 2 seconds or 32 entries. Background/generation changes discard queued writes and revoke commit leases. File staging performs its encoding/encryption off the UI isolate; the final validated rename runs synchronously on the caller's isolate after its lease check.

Read-cache content is a closed display-field projection of explicitly cached first-page GETs: project metadata/lists, non-confidential issues and their allowed threads/links, merge requests and allowed threads/approvals, individual pipeline/job metadata, confirmed-SHA files/tree/README, selected MR diff versions and verified terminal-job log tails with absolute offsets/truncation metadata. Public here means non-confidential content accessible to the bound account, including private projects. Public descriptions, comments, source, diffs and logs may themselves quote credentials or confidential text; projection/encryption does not redact these free-text secrets. No authentication/credential endpoint responses, confidential issues/internal notes, search/todos/events, GraphQL, HEAD/other non-GET responses, continuation pages, external/CDN responses, group objects and group-project/starred-project lists, branch/tag/commit objects, pipeline/job lists or other unlisted subresources enter this disk store. Full-path subresources and unconfirmed/non-SHA files/tree are excluded; unconfirmed `textFile` remains a network read. Unsupported query keys/representations fail closed. `Cache-Control: no-store` forbids storage and retires an older exact-key disk value; server `max-age` does not set app freshness. Durable keys bind account, GET path, semantic query and logical `Accept`, separating `application/json` from `text/plain`; changing Accept later through an arbitrary interceptor is outside this contract. AI reads reject disk and memory values with disk lineage; AI preflight/readback remains on the network.

`ReadCacheDiskCoordinator.instance` keeps disk closed until readable settings/inventory, a current successful startup decision, recovery, verified account/generation activation and installed controls agree. Startup handles every pending marker first, including removed accounts, then deletes all read-cache keys/directories except the selected auto-resume account; setting `0` or sign-out pending retains none. Failed account-list/settings/inventory reads do not authorize orphan deletion. The read-cache, AI-history and AI-journal destructive recovery stages share a FIFO gate; a timed-out native operation holds it until actual quiescence, so permanently unacknowledged I/O can stall later cleanup (follow-up F1). Cold offline startup does not expose the disk cache: `/user` verification precedes activation. D1 sign-out includes account switching, `endSession` and removal; the departing binding is fenced synchronously before session/generation changes and key/directory deletion runs asynchronously. A bound terminal 401, or a terminal 401/user-ID mismatch while verifying a known-account candidate, also clears that account; a recoverable OAuth 401 does not clear disk. Ordinary mutable scope invalidation preserves pinned entries; permission revocation, D1/account clear, expiry and capacity eviction can remove them. Scope invalidation costs a secure-storage/Keychain marker write, its exact readback and a second marker verification, an ownership read before removal, then delete plus absence readback, along with key verification and file/index I/O; begin/end mutation barriers can each incur that cost, while overlapping scope work reuses its intent. Device call counts and p50/p95 latency remain unmeasured (follow-up F2).

Read-cache controls (我的 › 儲存與快取 › 離線快取, `lib/features/cache/read_cache_settings_page.dart`): device toggle, aggregate size and clear; the authenticated shell calls `installUserControls()` once the entry exists. Off synchronously closes the fence, attempts `0` plus readback, then clears pending intents, keys and directories, deleting each marker last; a failed preference write still enters cleanup and stays closed without claiming durable off. If the subsequent inventory read is unavailable, the current implementation stops before directory deletion, keeps cleanup pending and requires retry; successful deletion is not guaranteed. Off→on rebuilds only after cleanup, a read-back `1`, fresh recovery and a still-valid verified activation, so it takes effect at the next start or account switch; it never authorizes revival of pending old files. Same-session clear reopens only after complete cleanup for that binding. Full clear orders fence → marker write/readback → drain old I/O → delete key → delete directory → verify → remove marker/readback. Marker failure still attempts both deletions; key failure still attempts the directory. Normal completion/reopening requires both confirmed absent plus marker completion; proven-empty cleanup needs no marker. Account removal may proceed after either key or directory absence is confirmed, but incomplete cleanup retains its fence/pending state; neither confirmed means retain the account. Marker/key/directory failure together proves only this process is closed, not durable cleanup across restart. Read-cache cleanup does not touch AI history, journal keys/files or tombstones.

C3 prerequisites (storage/lifecycle only; offline saving, readers and UI remain separate): the coordinator inventories `offline_repo_key.v1.*`, `offline_repo_clear_pending.v1.*` and `offline_refused.v1.*`, and sweeps the separate `offline_repo/<hash>/` root. C2's 32/96 MiB accounting still counts only `read_cache`. Full account clear and device-off fence both namespaces, persist the C2 intent, drain C2 I/O plus the registered namespace's workers/maintenance, delete both keys before either directory, delete offline markers, and remove the C2 marker last. A C3-only pending clear preserves the identity-refusal marker; only same-user verification or account-level clear may remove that refusal. Unavailable ordinary inventory/settings do not authorize deletion. New C2-only repair and scoped-invalidation intents use marker JSON `{version:2,namespace:"read_cache",intentId,reason,requestedAt}` with `reason` restricted to `keyRepair` or `scopeInvalidation`; legacy v1 and unknown markers retain full-account recovery semantics. Existing encrypted entries/indexes, key names and AAD are unchanged, so no encrypted-file migration or opportunistic rewriting occurs. A failed full-marker write still cannot prove durable cleanup across restart.

Offline repository snapshots (C3a core, C3b UI): `getApplicationSupportDirectory()/offline_repo/<sha256(account.key) first 32 hex>/`, a sibling of `read_cache/`, holds `index.v1.bin` (snapshot list plus account metadata, including `lastValidatedAt` and the informed-consent time `consentAt`), `t_<snapshotId>.v1.bin` (one tree per snapshot), `b/<name>.v1.bin` (blob contents deduplicated by `HMAC(namesKey, objectFormat:blobId)`, first 32 hex) and `tmp/<jobId>/` while saving. Every file is AES-256-GCM `version(1) || nonce(12) || ct || tag(16)` (29-byte overhead) with AAD `jsonEncode(["offline_repo", 1, account.key, <relative file name>])`; snapshot and job IDs are validated 32-hex values and every directory level is checked with `followLinks: false`. Only text files (valid UTF-8, no NUL, ≤ 2 MiB and ≤ 20,000 lines; LFS pointers as text) and images (≤ 10 MiB) are stored, each verified against the tree's blob ID after reversible CRLF/`$Id$` normalization; other entries are recorded as not saved with a reason (`tooLarge`, `binary`, `missing`, `mismatch`, `symlink`, `submodule`, `unsupportedType`). Limits: 5,000 tree entries in at most 50 pages, 4 MiB tree and 1 MiB index plaintext, 300 MiB compressed archive and 1 GiB processed, 150 MiB stored per snapshot, 600 MiB per account and 30 snapshots (an update replaces its snapshot); a full device is ENOSPC (`deviceFull`) and keeps the old snapshot. Commit order: index entry `saving` → pending tree → blobs (temporary file then rename) → final tree read back → index `complete` read back (the commit point) → superseded tree removed and `gcPending` set. Recovery and GC run only in `ready` with no worker: `tmp/` is deleted, idle `saving` becomes `paused`/`interrupted`, `paused`/`failed` older than 24 hours are removed, and GC keeps the `saved` blobs of complete snapshots plus every blob of unfinished ones. Tree and archive responses carrying `no-store` end the save as `serverForbidsStorage`. The directory is excluded from iOS backup through the `mergeline/backup` channel that `tool/bootstrap.py` adds (an existing runner needs re-bootstrapping); Android already disables backup. The UI (C3b, `lib/features/offline/`) never writes these files itself: saving goes through `OfflineRepositories` (one per authenticated generation, exposed by `OfflineScope` above the navigator), browsing through `SnapshotRepositoryReader`, and nothing is written before the account's first save is confirmed in the informed-consent explainer. 我的 › 儲存與快取 › 離線專案 lists them; "clear cache" and turning the offline cache off say how many offline projects and how much space they delete (L1), and every way out of the session (`_leave` with a `LeaveIntent`, the account sheet, `endSessionFrom`, `FailureNotice`'s switch, account removal) confirms the loss before the AI guard. A snapshot view under `NetworkBoundary(offlineSnapshot)` opens no browser, share sheet or download, and `MarkdownView(snapshot:)` reads repository images only from the snapshot (never `rawFileBytes`), showing uploads and external media as placeholders; the AI `offline` flag is unchanged. Offline read-only mode (C3c) reads the same files without a client: in `offlineReadOnly` the coordinator allows index, tree and blob reads and explicit deletion (one snapshot, or all), and no recovery, GC, migration, `tmp` cleanup, blob or read-cache writes, key creation or `lastValidatedAt` update. Where no signed-in shell exists (the resume screen, the sign-in screen, the offline shell), the §6.7 confirmation counts the leaving account's snapshots with `ReadCacheDiskCoordinator.offlineSnapshotSummary`, which only reads the key and index; the sign-in screen asks before another saved account, a token or GitLab sign-in, or removal of the retained account (`leavingDiskAccountKey`: the recovered `diskRetainedAccountKey`, or before startup recovery the current decision's resume account, the same source `select` clears), and not for a retry of that account itself.

`ReadCacheNamespace` registration supplies synchronous fences/open admission and asynchronous stop/key/directory/marker hooks; late registration stays fenced until activation validates its markers. Backgrounding pauses C2 writes without fencing C3 workers. Closed-state offline eligibility reads never create keys or delete files; the owner/generation/epoch/pref gates are rechecked before offline admission. Every verified session activation fences other known accounts before binding and deletes them in the background. A same-account retry while no account is active preserves retained data and last-active unless identity is refused. Authoritative numeric project-security events can be forwarded directly through `ReadCacheNamespaceSecurity`, without UI subscriptions; HTTP classification and actual project-worker deletion belong to C3a/C3c.

Read-cache platform limits: Android templates exclude app data from backup/device transfer. iOS files use the platform default `CompleteUntilFirstUserAuthentication`; no stronger file-protection class or `isExcludedFromBackup` is set here. The account store, read-cache settings/keys/markers and AI secure stores use `KeychainAccessibility.unlocked_this_device` (`ThisDeviceOnly`); restored files whose account/key did not migrate are cleaned by startup. App lock covers the screen and does not revoke encryption keys: when the device Keychain is accessible after unlock, the cache remains decryptable behind that screen. Explicit iOS backup exclusion is a follow-up, and iOS device runs are `NOT_RUN`; Android run-as/backup/restore acceptance is also `NOT_RUN` for this documentation packet.

AI write journal: `getApplicationSupportDirectory()/ai_write_journal/<sha256(account.key) first 32 hex>/journal.v1.enc`, separate from `ai_history/`. It holds write metadata only: no bodies, file contents, attachment bytes, upload URLs, credentials or provider replay. It is encrypted with AES-256-GCM (a fresh 12-byte nonce per write; AAD binds version, account and file name) and is rejected above 1 MiB before decryption. At most 200 entries for 7 days; `dispatching` and `writeUncertain` entries are never pruned; at most 2,000 conversation counters, dropped after 90 days unused. Writes use an exclusive temporary file, `flushSync` and `renameSync`, with no links or `.`/`..` in the path. `main.dart` configures it at start-up and recovers it once the account list has loaded, whatever the AI build flag, so a removal can always clean up; a failure leaves the journal refusing writes. An account added later (a first sign-in, a second account), or one whose recovery failed, runs the same recovery before its first write. It is deleted by account removal, by a reset (first step, after the reset marker is durable), and by orphan cleanup of accounts that are no longer stored. A file without a readable key is never deleted automatically. AI attachments stay in memory only: they are dropped with the conversation and never written to disk.

Outside secure storage: the gitlab channel's update APK `getTemporaryDirectory()/updates/gitlab-mobile-<versionCode>.apk`, written only after the user taps 下載, named only after its size and SHA-256 match GitLab's record, and deleted at the next start and before every download. Artifact cache `getTemporaryDirectory()/artifacts/<sha256(account.key) first 32 hex>/<projectId>-<jobId>/<stamp>-<attempt>/`. Removed on account removal. A failed removal keeps the account and reports 無法清除產物. The operating system may purge the directory. Two plugin copies are transient: share_plus copies a shared archive into `<cache>/share_plus/` (deleted at once after a dismissed, unavailable or failed share; after a successful share on the next resume after the app left the foreground; always before the next share and on account removal, best-effort), and image_picker / file_picker copies of a picked attachment are deleted right after their bytes are read (`discardPickedCopy`, cache paths only).

Markdown media: repository images use authenticated, bounded raw-file requests pinned to the Markdown base ref; external HTTPS images use a separate credential-free client that rejects a name if any resolved address is private and pins a checked address while verifying TLS for the original host on every redirect hop. HTML images, SVG and tap-to-load audio/video render in the app; media never starts from rendering alone. Known limitations: branch refs containing `/` in absolute raw/blob URLs are ambiguous, and Git LFS files return pointers only.
Inline HTML follows CommonMark (tags only); raw-text semantics apply in HTML blocks only. Consequently, an image inside an inline `<script>`, `<style>`, `<textarea>`, `<title>` or `<noscript>` renders (GitLab web hides it), and inline audio/video fallback content is hidden only when it is plain text and complete tags within 4096 characters and 16 tags. Markdown longer than 65536 characters is not rendered.

Playback staging: `getTemporaryDirectory()/media/<sha256(account.key) first 32 hex>/<stamp>-<attempt>/<sanitized filename>`, limited to 100 MiB per download. Each card owns one attempt, removed after playback disposal or cancellation; account removal clears that account's directory and propagates cleanup failures. The shared launch hook (`registerBundledLicenses`, called before `runApp`) starts removal of the entire previous-run media directory, even while signed out; new downloads await that same cleanup before writing. This cache can be purged by the operating system. Images and per-view caches remain in memory.

Opt-in AI chat history lives under `<application-support>/ai_history/<sha256(account.key) first 32 hex>/` (`Directory.systemTemp` under `FLUTTER_TEST`). Each account has `index.v1.bin` and conversations named `c_<32 lowercase hex>.v1.bin`; validate the ID before joining a path. Files contain AES-256-GCM encrypted, redacted display models only: user text up to 16,000 code units, assistant text up to 64,000, context metadata and excerpts up to 8 KiB, tool rows and result excerpts up to 8 KiB, usage and finish reason. Never persist `ProviderOutputEntry`. Every write uses a fresh 12-byte nonce and AAD binding the envelope version, account and file name; JSON encode/encrypt and decrypt/decode run in an isolate. Check ciphertext size before reading (conversation 640 KiB, index 256 KiB). The plaintext limit is 512 KiB per conversation; encrypted storage is bounded to 50 conversations and 16 MiB per account, 64 MiB per device, with 7/30/90-day retention (default 30). Capacity accounting reserves a full 256 KiB index envelope per active account transaction and includes existing indexes in the device total. Device eviction uses file modification time and protects accounts until a complete history scan succeeds in this process, including unknown accounts and accounts whose key alone has loaded. It also skips accounts with unavailable/missing keys, active cleanup or an authenticated unsupported index/conversation (including their index files), and invalidates foreign indexes after deleting their files; their next read rebuilds them. Degrade oldest tool excerpts to metadata before refusing further saves, and surface that refusal; never stop saving silently.

`AiHistoryCoordinator.instance` is the process-wide owner of every AI history read, write and cleanup. All `ai_account.v1.*` mutations share `AiAccountMutationCoordinator`: re-read inside one process-level account queue, fence queued settings/history mutations before cleanup, invalidate settings caches, release cancelled or failed orphan-cleanup leases, and reopen completed cleanup for current session members, including retained accounts after recovery or failed session removal. Removal cleanup stays fenced until that outer session boundary completes. Per-account states are `unknown`, `disabled`, `ready`, `readFailed`, `unavailable`, `keyMissing` and `cleaning`; secure-key reads distinguish `found`, `absent` and `unavailable`. An unavailable key is neither absent nor permission to delete data: retry after 1, 5 and 30 seconds and on later resumes. Start-up recovery runs regardless of the feature gate, and account-record/history-key orphan cleanup and directory deletion run only after `SessionController.accountsLoaded` proves a current, successful account-list load. Recovery rebuilds a missing or undecryptable index from readable conversations, drops index entries whose files are missing, restores unexpired orphan files, removes stale `.tmp` files older than one hour, removes and reports an individually undecryptable conversation, then reapplies retention and capacity. Startup also applies retention/capacity from authenticated index metadata for verified supported conversation versions. Index entries carry conversation format version, update time, byte size and file modification time; entries with unsupported versions are protected, and entries missing a verified version are opened before retention/eviction; ordinary saves decrypt the index and only changed/unindexed/unverified files, commit the new conversation, then update/evict by metadata. Blocking bounded reads and atomic writes run off the UI isolate. Every directory from the trusted root through the account is checked for links/types; temp files use random exclusive creation and destinations must be regular files. Authenticated unknown schema/version/fields are retained, skipped and reported as unsupported; their IDs are quarantined from same-ID saves, retention and eviction while counting toward account capacity, and an unsupported index exposes an explicit clear action; only envelope, size and authentication failures remove conversations. Removed-conversation, stale-temporary-file, repaired-index and unsupported notices accumulate until explicitly acknowledged. File-I/O read failures retain the key in `readFailed` and allow explicit retry without secure-key retry timers. A successful subsequent save returns the account to `ready` and clears its read-failure notice. Recovery interrupted by account membership changes repeats against the current successfully loaded account set until that set remains stable. Per-account startup failures do not skip other accounts, and malformed secure inventories are skipped individually and reported. File-I/O save failures expose a per-conversation not-saved state without entering the secure-key retry machine. Oversize conversations, capacity refusals and device-capacity evictions are separate. Oversize conversations keep their permanent not-saved latch; a capacity refusal returns `storageLimit` with its own retryable notice that space is currently full and saving resumes when space frees, and capacity-refused or evicted conversations may save again after space frees. Conversation writes rename the conversation before the index; eviction deletes the conversation before updating the index. On iOS, both the account list and history keys use `ThisDeviceOnly` Keychain storage. A full restore therefore has no accounts: after the empty account list loads successfully, orphan cleanup removes restored history files and secure AI records/keys. `keyMissing` applies to partial Keychain loss when the account list survives; it offers an explicit clear action and never authorizes automatic deletion.

Account removal order is `clearSecureDrafts → clearAccountArtifacts → clearRecentProject → clearReadCacheDisk → clearAiAccountData → session.remove`, with the existing AI-journal removal-start mark between read-cache and AI cleanup when required. `session.remove` repeats artifact/read-cache cleanup inside its commit fence before saving the account list. AI cleanup first writes the tombstone and enters `cleaning`, invalidates pending work, clears plaintext caches and waits for active writes; it then deletes the history key, history directory, AI account record and finally the tombstone. Failures in deletion steps retain or reassert the tombstone and keep the account, raising the translated AI-history cleanup failure. If the initial marker write itself is unavailable, the account stays and explicit retry is required; a durable marker cannot be promised until a write succeeds. This sequence is unconditional even while the AI gate is false.

### Localization

The app is written in Traditional Chinese and translated into the languages listed in `tool/l10n.py` (`LANGUAGES`; zh-TW first). ## CI facts that affect contributors

### AI runner (MR4; on in gitlab builds since v0.6.0)

`AiRunner` owns an in-memory conversation. It sends at most six model requests
per user send and uses the read-only `AiGitLabReadPort`; only
`lib/core/ai/tools/gitlab_read_port.dart` imports `GitLabApi`. Tool scopes contain
identity and pinned revisions, never account objects. Sensitive-path filtering
is shared by initial context and tools. A whole fetched source is stripped of
ANSI and redacted before taking excerpts; line-aligned diffs use fragment
redaction. Propagate the first `withheldPrivateKeyContext` flag from context and
tool executions to the runner/display model; rescanning placeholders cannot
recover that notice.

Use one `KnownSecretsLive` for the conversation and pass its `refresh` to both
the runner and catalogue. It reads keys from the process-wide settings owner and
rereads the current GitLab access/refresh values before redaction, retaining the
union until the conversation is discarded. Settings initialization increments
`secretSetId` whenever loading changes the provider-key set, so a live-secret
reader that refreshed before initialization will refresh again afterward.
Construct `AiRunGuard` from the current session generation, exact API identity,
provider recipient revision and
`AiSettingsController.isValid(accountKey, contract)`. `AiRunnerBinding` listens
to that settings owner and session so a stalled stream also stops immediately;
dispose the binding with its conversation. Production wiring passes
`AiTransport.cancelActive` separately from terminal `close`: user stop and
model/run timeouts cancel only active requests so the same wire client remains
usable for a follow-up, while disposal, recipient replacement and
`stoppedBySettings` close the transport. Each catalogue send gets a fresh
`AiToolBudget`; wire `resetToolBudget`, `beginToolTurn` and
`toolBudgetExhausted: () => budget.exhausted`, and call `beginTurn` before each
tool batch. `executeTool` must call `executeResult` and return results carrying
`AiAppText` in `data`; production code must not construct content-only tool
results. Do not share a budget between sends. The catalogue reserves twice
each logical read cost to cover GitLabApi's single OAuth retry; the HTTP counter
is a conservative allowance. `executeResult` propagates provenance plus
withheld-private-key, truncated and blocked-sensitive metadata in
`AiToolResult`; tool results retain escaped, nonce-labelled untrusted-data
blocks. App-owned context and tool values retain an `AiAppText` plain model;
redact and re-verify its strings before JSON/XML/label escaping. Encode only for
delivery. Summaries retain plain text and escape once per encoding. Never decode
wire escapes to search for secrets; provider verification reads only the plain
strings produced by the decoder, excluding opaque fields. A clipped value keeps
only the deliverable plain prefix. A private marker travels with each cut string,
including JSON values, through key collisions and projection composition. Each
redaction trims a trailing partial known secret from that string. Known-secret
matching and cut-end trimming also use each secret's cached pattern-only alias
when intake redacted its head before it became known. Only aliases keeping at
least four characters of their secret are cached; shorter remainders (one
trailing space, `.x`) would match ordinary text beside a marker and are an
accepted residual. Alias cut-end trimming must extend beyond
the leading replacement marker into retained secret characters. A secret already
sent before it became known remains a residual. Two further residuals remain:
a pattern starting before the secret in surrounding text and ending inside it
can produce a different alias layout; a late secret that contains a previously
known secret is split by that secret's replacement and, with or without a cut,
is not covered by its alias (R5-NEST). Do not treat those layouts as covered by
pattern-only aliases.

The runner's 64,000-character answer clips and history codec's 16,000/64,000-
character and 8 KiB truncations have no cut markers. `restoreFromDisplay` can
feed them into projections; today they hold provider-produced or already-sent
text. MR5/MR6 must re-evaluate those cuts before restoring history to a different
recipient.

Frozen wire fragments are append-only and never rewritten. A newly known secret
in app/provider text that was already sent stops the current send because sent
content cannot be retracted; verification also checks the cached aliases. The
next send starts from a freshly
redacted projection. Key replacement uses `replaceKeyRecipient` and a
new wire client/transport, preserving consent only when the recipient contract
is otherwise identical. Other recipient changes require a new conversation.
A binding failure also requires a new segment. `restoreFromDisplay` initializes
an idle conversation from redacted history models via a new projection; it never
restores provider replay output. Every frozen tool call has a
result, including stopped and exhausted calls. A soft timeout keeps the source
read owned until it settles, preventing overlapping GitLab reads across sends.
For display wiring, `onTextChanged` receives cumulative redacted snapshots at
exponentially increasing character thresholds so repeated redaction remains a
linear scan overall. `onToolStarted` receives an `AiToolCall` with its redacted
name and, for display only, the top-level scalar arguments under simple keys with
control characters stripped and values redacted (long or nested values are left
out, never cut); `onToolResult` receives every safe result, including
synthetic terminal results used to pair unfinished calls. `onEvent` receives
usage and finished events. Partial output recovered after stop is display-only:
refresh secrets and recheck the guard within `toolDeadline`, then redact it; it
is never frozen or replayed. After `stop()`, await the active `run()` before
enabling a follow-up: recovery can wait up to `toolDeadline` for a secret refresh,
and the runner remains busy until recovery finishes.
Cleartext requests check interfaces with `includeLinkLocal: true`; missing or
unavailable interfaces require per-send confirmation. These checks do not prove
same-subnet reachability. `MERGELINE_AI_ASSISTANT` defaults to false; since v0.6.0
(owner decision, 2026-10-30) CI compiles the gitlab flavour with it true. Play stays off.

The chat (MR6a) sits on `AiChatSession` (`lib/features/ai/ai_chat_session.dart`):
`AiChatController` owns one runner per conversation and reports display items,
phase and blocker. `AiRunRegistry` keeps the account's conversations above the
navigator, keyed by origin (job, issue or merge request, file at a SHA,
`group-item:<groupId>:<iid>` or
`group-page:<viewGroupId>:project:<projectId>:workItem:<iid>`), so a
run continues after its page closes.

At most three run at once; an idle session
then reports `tooManyRunning`. A new account generation disposes them all.
Every page calls `release` on its session when it closes; the registry counts
open pages and, after the last, drops a session that holds nothing, so the
next visit reads the page again. The "AI summary" request belongs to the visit
(`AiChatPage.summarize`), not to the kept session. GitLab reads that fail keep
their `ApiFailure` (shown with `FailureNotice`); provider failures are
`AiFailure`. Anything shown outside the display items (the title) goes through
`displaySafe`, which never throws and returns an empty string for text it
cannot check.
